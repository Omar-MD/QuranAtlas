# Private Qaloun PDF Mushaf Edition Design

## Purpose

This specification adds a second Qaloon Mushaf edition to a private QuranAtlas build while preserving the current quran.ws Mushaf. It defines a deterministic PDF import, a page-map compatibility proof, a media-capable page contract, one-time edition selection, and configurable page framing that can show the complete side lane or remove it to enlarge the Qur'an text.

The reader remains page-based. The source PDF is never loaded or parsed in the browser.

## Source Facts

The private source is:

- original filename: `Noor-Book.com  مصحف رواية قالون عن نافع طبعة جديدة.pdf`;
- SHA-256: `4454431b2662bc10060cc9335ba13baabe1f18a6762c492d41ccf11a4083012f`;
- document pages: 630;
- source page size: `512.545 x 652.654 pt` CropBox;
- logical Mushaf pages: PDF pages 5 through 608 map to printed pages 1 through 604;
- PDF pages 1 through 4 and 609 through 630 are not reader pages;
- the PDF is vector/font based and contains no embedded full-page raster images;
- the PDF permits printing but restricts copying;
- the cover labels the source as the fourth edition, 2023.

The stable private edition identity is `qalun-furatiyyah-2023-v1`, with display label `Qalun Furatiyyah 2023`. The runtime riwayah key remains `qaloon` for compatibility with the current QuranAtlas data model.

The source PDF stays outside Git and outside `public/` and `dist/`. A private import command receives its local path, verifies the exact checksum before doing any work, renders and validates the complete selected range in scratch staging, and atomically promotes only complete derived artifacts into normalized build directories.

## Goals

- Keep the current `qalun-quran-ws-v1` edition fully supported and unchanged.
- Build the private edition from one pinned PDF without adding a runtime PDF engine.
- Prove whether the private edition shares QuranAtlas's existing canonical Qaloon page boundaries before introducing any new mapping data.
- Preserve existing Mushaf routes, navigation, gestures, bookmarks, Daily Wird integration, Single/Scroll layouts, and responsive behavior.
- Keep mobile memory and main-thread work bounded.
- Preserve sharp Arabic text, diacritics, colored pronunciation marks, borders, and side-lane content.
- Remove PDF media-box whitespace before page assets are emitted.
- Let the reader show the complete side lane or hide it completely while keeping all Qur'an text reachable.
- Let new or cleared private-build installations choose one Mushaf edition during setup.
- Keep existing installations on the current quran.ws edition without prompting or resetting them.

## Non-Goals

- Runtime PDF.js, browser PDF rendering, range-requested PDF pages, or shipping the source PDF.
- Arbitrary user PDF import or a generic Mushaf-import UI.
- Riwayah, translation, tafsir, or general reader-profile selection.
- Routine edition switching in Settings.
- Edition-aware bookmark schemas or preservation of page bookmarks across an edition switch.
- A targeted partial-edition reset. Edition changes use the existing Clear All Data flow.
- Pinch zoom, free panning, a generic crop editor, or user-authored per-page crop rectangles.
- OCR, selectable Mushaf text, ayah hit regions, commentary extraction, or pronunciation-rule parsing.
- Dark recoloring, CSS inversion, or generated dark variants of the private pages.
- Full-Mushaf offline installation, quota management, or download progress UI.
- Reformatting the existing quran.ws SVG page bodies.

## Decision Summary

- Import only PDF pages 5 through 608 and apply the PDF CropBox before any additional framing.
- Compare page boundaries by visible Qur'an wording and canonical Qaloon references, not by the PDF's printed verse numbers. Reuse the existing Qaloon map only after all 604 page starts pass the compatibility gate.
- Store normalized inputs and generated outputs by riwayah and edition, not by riwayah alone.
- Make the builder's explicit selected edition set authoritative: preserve every selected sibling and remove every unselected edition from output and indexes.
- Keep the standard build on the current edition. A private build explicitly includes `qalun-furatiyyah-2023-v1` when its verified local source is available.
- Run a representative media spike before freezing the private page format.
- Prefer sanitized external SVG rendered through `<img>` when it passes the mobile gate. Use measured WebP variants only if SVG fails the gate.
- Keep the current inline-SVG runtime path for `qalun-quran-ws-v1`.
- Add one external-image manifest descriptor for the private edition's measured winning format and normalized page-frame rectangles.
- Keep one active `mushafEditionId`. Fresh or cleared private builds choose once; existing installs retain quran.ws.
- Use Full page, Text focus, and a bounded framing slider. Any non-zero focus value uses width-based rendering and native vertical scrolling.
- Use immutable versioned URLs. Regenerated bytes require a new edition version or content identity.

## Correctness Gate: Page-Map Compatibility

Printed verse markers in the private PDF are not QuranAtlas's canonical Qaloon verse keys. A numeric comparison therefore produces false mismatches. Verified samples show the same first visible wording as the current Qaloon page map:

- private printed page 8 displays printed `2:49`; the same wording is QuranAtlas Qaloon `2:48` and is the existing page-8 start;
- private printed page 304 displays printed `18:98`; the same wording is QuranAtlas Qaloon `18:94` and is the existing page-304 start;
- private printed page 306 displays printed `19:12`; the same wording is QuranAtlas Qaloon `19:11` and is the existing page-306 start.

The implementation first tests compatibility with `data/normalized/quran/riwayat/qaloon.json`, SHA-256 `18465c40ebeec40a92eb98745c9b89796ac6e31f6e93988883dfb6602faaea95`. It translates the PDF's printed markers through `public/dataset/translations/_verse-aliases.json`, SHA-256 `1df390b3cd73ba69502062a4fcab9d062a01b24cebda39c629bb4e50974bd450`, and then compares visible first Qur'an wording. Raw printed marker numbers are never compared directly with QuranAtlas Qaloon keys.

A committed compatibility record is a data invariant:

```ts
type MushafPageMapCompatibility = {
  version: 1
  mushafEditionId: 'qalun-furatiyyah-2023-v1'
  sourcePdfSha256: '4454431b2662bc10060cc9335ba13baabe1f18a6762c492d41ccf11a4083012f'
  pageMapSource: 'data/normalized/quran/riwayat/qaloon.json'
  pageMapSha256: '18465c40ebeec40a92eb98745c9b89796ac6e31f6e93988883dfb6602faaea95'
  verseAliasSource: 'public/dataset/translations/_verse-aliases.json'
  verseAliasSha256: '1df390b3cd73ba69502062a4fcab9d062a01b24cebda39c629bb4e50974bd450'
  pageCount: 604
  sourcePdfPageOffset: 4
  pageStartReviews: Array<{
    page: number
    sourcePdfPage: number
    canonicalFirstVerse: QuranRef
    result: 'wording-match'
  }>
}
```

The 604 `pageStartReviews` rows are a committed manual-review record bound to the pinned PDF, Qaloon source, and alias digests. For each rendered page, the reviewer records the canonical first verse only after visually confirming that its opening Qur'an wording matches. The rows are validation evidence, not a second runtime page map; the builder requires each recorded reference to equal the first reference derived from the pinned Qaloon source.

The compatibility gate MUST establish:

- exactly 604 ordered PDF reader pages;
- `sourcePdfPage === page + 4` for every page;
- the first visible Qur'an wording on every private page matches the existing canonical Qaloon page start after alias resolution;
- continuing verses and Surah transitions preserve the current first-page mapping semantics;
- the first page begins with Al-Fatihah and the final page includes Surah 114;
- the current `verseToPage`, first-verse, last-verse, Verse-to-Mushaf bridge, and page-based Wird fixtures remain valid for the private edition;
- manual visual review establishes visible-wording equivalence for all 604 page starts, with the three numbering-convention samples retained as regression fixtures;
- automated validation proves the record has exactly one ordered match row per page, matches the pinned digests and derived first references, and contains the required regression fixtures. It does not claim to infer wording equivalence from rendered pixels.

When the gate passes, the private edition reuses the existing Qaloon map and builder derivation. If any true wording/page-boundary mismatch appears, implementation stops. A separately owned edition map is not added under this specification; it requires a focused follow-up design rather than silently expanding this plan to maintain a second 6,236-verse mapping.

## Private Input And Build Profiles

The catalog describes the private edition without committing the PDF or an absolute machine path. It records:

- edition id and display label;
- `sourceKind: "local-pdf"`;
- expected stable source filename;
- exact SHA-256;
- document page count 630;
- reader source range 5 through 608;
- logical page count 604;
- output media policy and transform version;
- private-use provenance notes.

The import accepts an explicit local PDF path. It fails before writing output when the file is missing, has the wrong digest, has the wrong page count, or cannot render the required page range. It renders all 604 pages and metadata into a new scratch staging directory, validates the complete staged edition, and only then atomically promotes the directory to the normalized edition path. A failed import leaves the previously validated normalized edition unchanged and removes or ignores the incomplete staging directory.

Normalized and generated paths include both identities:

```text
data/normalized/mushaf-pages/qaloon/qalun-quran-ws-v1/**
data/normalized/mushaf-pages/qaloon/qalun-furatiyyah-2023-v1/**
public/dataset/mushaf-pages/qaloon/qalun-quran-ws-v1/**
public/dataset/mushaf-pages/qaloon/qalun-furatiyyah-2023-v1/**
```

The default repository/CI profile selects only quran.ws. The private profile explicitly selects both editions and requires the local private input or already validated normalized private artifacts. Default CI MUST NOT claim it rebuilt or validated the private page bodies when the private input is unavailable.

The builder receives the complete selected edition set for a riwayah before it emits or prunes anything. That set is authoritative:

- the standard set contains only `qalun-quran-ws-v1`, preserves its output and index entry, and removes any stale private-edition output and index entry;
- the private set contains both edition ids and preserves both outputs and index entries;
- pruning runs once per riwayah after the complete selected set is known, never once per edition.

The quran.ws page bodies and edition manifest remain byte-for-byte unchanged when the private edition is added; only the shared asset index intentionally gains the private entry.

## PDF Framing And Whitespace Contract

Poppler conversion MUST use the PDF CropBox. The larger MediaBox contains false outer whitespace and is not a reader frame.

The normalized import metadata carries two reviewed source rectangles:

```ts
type NormalizedRect = {
  x: number
  y: number
  width: number
  height: number
}

type MushafSourcePageFraming = {
  sourceFullFrame: NormalizedRect
  sourceTextFrame: NormalizedRect
  sideLane: 'left' | 'right' | 'none'
}
```

Source rectangle coordinates are fractions of the CropBox render, from 0 through 1. `sourceFullFrame` contains the complete printed page border and the complete side lane while removing all external top, bottom, left, and right whitespace. The emitter crops the page asset to this reviewed rectangle, so the complete emitted asset is the runtime Full page frame. `sourceTextFrame` contains the full Qur'an text frame and removes the complete side lane. It MUST be contained within `sourceFullFrame` and MUST NOT clip Qur'an glyphs, diacritics, verse markers, headers, footers, or the text-frame border.

The runtime manifest stores only the text rectangle transformed into emitted-asset coordinates:

```ts
type MushafPageFraming = {
  textFrame: NormalizedRect
  sideLane: 'left' | 'right' | 'none'
}
```

Runtime Full page is always the implicit unit rectangle `{ x: 0, y: 0, width: 1, height: 1 }`. This gives one owner to outer-whitespace removal: the build output, not CSS or runtime crop logic.

The side lane may contain commentary or pronunciation guidance, or it may be visually empty. QuranAtlas does not interpret that content. Full page always shows the lane completely; Text focus always removes it completely. Pages whose lane is on the opposite side use their own `sideLane` and rectangles. Special-layout pages receive explicit page-specific rectangles rather than unsafe parity assumptions.

Automated build validation checks source rectangle bounds, containment, the transformed runtime rectangle, and non-empty emitted pixels at every reviewed edge. Those checks cannot establish that Qur'an content is complete. A generated contact sheet or equivalent visual review artifact is therefore used for manual verification of all 604 Full page and Text focus frames. The review artifact remains scratch output and is not a product feature.

## Media Format Gate

The final private page format is selected by a production-browser spike, not assumed from file extension or compressed size.

The spike uses 12 to 20 representative pages, including:

- pages 1, 2, and 604;
- dense text pages;
- Surah starts;
- pages with red and blue pronunciation marks;
- pages with populated side lanes;
- pages with empty side lanes;
- both left- and right-lane templates;
- special first/last-page layouts.

Candidate A is a build-sanitized external SVG displayed through `<img>`. SVG scripts, event handlers, foreign objects, external URLs, remote fonts, and unsafe CSS references are rejected. Same-document references are allowed only when they pass the build allowlist. If faithful output requires constructs that cannot pass the safety contract, SVG fails the gate.

Candidate B is one or more measured WebP renditions generated from the CropBox source. Widths and quality are chosen from actual rendered-width and device-pixel-ratio evidence. The design does not mandate dual lossless renditions before measurement.

The production-preview comparison uses the same machine, browser version, throttling profile, representative page set, and cold/warm-cache sequence for both candidates and for the current quran.ws baseline. Required Playwright viewports are `390x844` at DPR 3, `844x390` at DPR 2, `768x1024` at DPR 2, and `1440x900` at DPR 1. Viewport emulation proves layout only. Before selection, the candidate also runs clarity, load/decode, ten-page-turn, and sustained-Scroll checks on at least one physical mobile device and browser in the intended private target class, recording its model, OS, browser, and results. If both iOS and Android are intended targets, one representative device from each class is required.

Each candidate MUST pass these objective gates:

- reviewed glyphs, diacritics, verse markers, colored marks, borders, Full page, and Text focus remain visibly clear at the required DPRs;
- no blank frame occurs after a preview is declared ready;
- the requested page plus immediate prepared previews transfer at most 4 MiB in the private serving environment;
- ten consecutive ready page turns produce no candidate-attributable main-thread long task over 100 ms;
- theoretical decoded residency for the current page plus prepared previews is at most 64 MiB;
- median requested-page-ready time is at most 1.25 times the current quran.ws median under the same profile;
- sustained Scroll mode keeps the existing logical window bounded and does not accumulate decoded pages;
- desktop browser zoom preserves readable marks and borders;
- production preview, rather than a standalone asset, passes every measurement.

External SVG is evaluated first and selected when it passes every gate. WebP is evaluated only if SVG fails at least one gate. The spike records one winner before runtime integration; the private build then emits only that format. If neither candidate passes, implementation stops instead of weakening the budgets or adding another runtime format branch.

## Manifest And Runtime Asset Contract

The private edition uses a media-capable manifest. Existing quran.ws manifests remain supported.

```ts
type MushafExternalImageSource = {
  assetPath: string
  bytes: number
  sha256: string
  width: number
  height: number
  mimeType: 'image/svg+xml' | 'image/webp'
}

type MushafPageMedia = {
  kind: 'external-image'
  fallback: MushafExternalImageSource
  sources?: MushafExternalImageSource[]
}

type MushafManifestPageV2 = {
  page: number
  media: MushafPageMedia
  framing: MushafPageFraming
  firstVerse: QuranRef
}
```

Manifest `assetPath` values are edition-relative. The top-level asset index resolves them beneath its absolute, immutable `/dataset/mushaf-pages/{riwayah}/{editionId}/**` base. The builder hashes the emitted bytes, writes the digest into the manifest source descriptor, and emits the same digest in the corresponding asset-index membership record. Runtime validation checks descriptor/index agreement, including the digest value, but does not refetch assets as blobs or rehash `<img>` responses. It also checks the riwayah, edition, page number, extension, MIME type, dimensions, byte count, and manifest membership. Runtime never accepts a media URL that is not declared by the active edition manifest and asset index. `sourcePdfPage` stays in normalized/build provenance rather than the runtime page record. The page's last verse is derived and validated from the existing canonical `verseToPage` data rather than duplicated in the private page record.

The runtime page state becomes a discriminated union. The quran.ws branch continues to carry sanitized inline SVG markup. The private branch carries a validated external-image descriptor plus framing metadata and renders it with `<img>` or `<picture>`. The same branch handles either measured MIME outcome, but one private build never emits both candidate strategies. `MushafPageViewer` renders both editions through the same page-cell, accessibility, gesture, bookmark, route, and scroll contracts.

## Page Loading And Mobile Performance

The existing five-entry logical page window remains. Media readiness and decoded-media residency are treated separately.

- The requested page has highest priority.
- Single mode eagerly prepares the requested page and immediate previous/next preview only.
- Pages two positions away remain descriptor-only until Scroll mode or navigation makes them relevant.
- If WebP wins the media gate, only the current/dominant page may request the highest proven rendition eagerly. Immediate neighbors use the lower proven preview rendition; farther pages stay lazy.
- Scroll mode promotes the dominant and near-visible pages while keeping the retained logical window bounded.
- A preview is ready only after the browser has successfully loaded and decoded the selected `<img>` resource. Descriptor availability, request completion without decode, or a stale load from another edition is not readiness.
- A page cannot become a swipe destination until its selected preview is ready.
- Load, decode, cancellation, and stale-edition failures clear the affected pending preview without replacing the current page; a later navigation may retry it.
- Failed or cancelled neighbor loads never discard the current page.

The framing control reuses the same media asset. Showing or hiding the side lane does not fetch a second page asset.

## Page Framing Interaction

The active private edition exposes three coordinated controls in Mushaf Page layout settings:

- `Full page`: framing value 0;
- `Text focus`: framing value 1;
- `Qur'an text size`: a bounded slider between the two verified frames.

The stored value is:

```ts
type MushafPageFramingValue = number // normalized and clamped from 0 through 1
```

The displayed percentage is derived from the current interpolated frame width; it is not a free scaling multiplier. The runtime linearly interpolates the implicit unit Full page rectangle and the reviewed `textFrame`. The page-specific interpolation automatically removes a left or right lane without horizontal panning.

At framing value 0, the reader retains the user's existing Fit page/Fit width preference. Any value greater than 0 uses effective Fit width so the Qur'an text genuinely enlarges and the complete interpolated frame remains horizontally visible. This 0-to-positive transition is an intentional preset boundary, not continuous free zoom: Full page honors the stored fit preference, while every focused value enters the same width-based reading mode. The Mushaf stage owns native vertical scrolling until the bottom of the frame is reachable. Returning to Full page restores the stored Fit page/Fit width behavior.

Framing applies consistently in Single and Scroll navigation. Changing framing:

- does not change the route or bookmark target;
- keeps the current/dominant page anchored;
- clamps the native stage scroll offset after layout;
- never adds horizontal stage scrolling;
- never clips the top or bottom of the selected frame;
- remains usable in compact landscape and safe-area layouts.

The framing controls appear only when the active edition declares valid framing metadata. quran.ws retains its existing settings and behavior.

If a page has missing or invalid framing metadata at runtime, the viewer fails open to the complete emitted page asset and disables Text focus for that page. It never guesses a crop.

## Setup, Migration, And Switching

QuranAtlas continues to store exactly one active `mushafEditionId`.

- Add a separate versioned Mushaf-edition setup marker, such as `mushafEditionSetupVersion`. Do not change or repurpose the existing `MVP_ASSET_CONTRACT_ID`; changing it invokes the existing destructive asset-contract reset.
- Migration inspects the pre-existing asset-contract marker before writing default setup state. An installation with the existing valid marker and no new setup marker is atomically assigned `qalun-quran-ws-v1` and marked setup-complete while preserving settings, bookmarks, continuity, caches, and IndexedDB data.
- Existing users are never prompted, reset, or moved to the private edition during upgrade.
- A genuinely empty or cleared private-build installation, identified by the absence of both a valid existing marker and a completed edition setup marker, loads the built Mushaf asset index.
- When two compatible Qaloon editions are built, setup asks the user to choose one edition.
- When only one compatible edition is built, setup selects it and continues without presenting a false choice.
- Setup writes the selected edition id and completion marker in one storage transaction or an equivalent recoverable commit; neither value is considered valid alone.
- A fresh deep link is retained through setup and resumed after a valid selection.
- A selected edition must exist in the built asset index before setup can complete.
- A completed selection whose edition is missing from the runtime index renders a missing-edition error and directs the user to Clear All Data. It does not reopen setup while page bookmarks from the old edition still exist.

There is no edition selector in ordinary Settings. To change editions, the user uses About > Clear All Data, which clears settings, page and verse bookmarks, continuity, and caches under the existing product contract. The next launch returns to setup. No page bookmark is carried from one edition to another, so bookmark storage remains unchanged.

## Cache And Offline Behavior

Private page assets follow the current on-demand dataset policy:

- `/dataset/indexes/mushaf-assets.json` is a narrow exception to the generic dataset CacheFirst route: serve this mutable availability index with NetworkFirst and a cached offline fallback, so an online setup or launch observes the current build's selected edition set;
- a cached availability index may support an offline launch, but it is not accepted as evidence that a removed edition exists once a current network response is available;
- page assets are excluded from shell precache;
- visited page assets may be stored by the existing CacheFirst dataset route;
- an offline revisit works only for the exact previously fetched asset or rendition;
- a different viewport or device-pixel-ratio choice may select an unfetched rendition and use the existing unavailable/error treatment while offline;
- an unseen page while offline uses the existing unavailable/error treatment;
- the product does not claim that the complete private Mushaf is installed offline.

Every private edition URL includes immutable edition identity. Changed source bytes, transforms, framing, map data, or output encoding require a new edition version or content identity. A build MUST NOT overwrite bytes at an already released immutable URL.

## Error Handling

- Missing or wrong private PDF: fail import before output mutation; incomplete staging is never promoted.
- Wrong checksum, page count, or source range: fail import.
- Any true page-boundary mismatch: stop private-edition implementation and require a separate mapping design.
- Invalid framing rectangle or a frame outside the asset: fail build.
- Unsafe SVG or external reference: fail the SVG candidate; do not weaken the sanitizer.
- Both media candidates fail at least one required budget: stop private-edition implementation; do not add more runtime format branches under this specification.
- Missing completed selected edition in the runtime index: show the missing-edition error and require Clear All Data before another setup selection.
- Requested-page failure: use the existing visible reader error state.
- Neighbor load, decode, cancellation, or stale-edition failure: keep the current page and allow a later retry.
- Invalid runtime framing: show the full asset and disable page focus rather than crop.
- Failed preference persistence: retain the existing safe preference fallback and never block page reading.

## Verification Strategy

### Data And Build Tests

Durable data/build validation and required manual review artifacts establish:

- exact checksum enforcement;
- CropBox conversion rather than MediaBox conversion;
- PDF pages 5 through 608 become logical pages 1 through 604;
- front/back matter is excluded;
- explicit multi-edition selection preserves both selected editions;
- a private build preserves both selected sibling editions;
- a subsequent standard build removes the unselected private output and index entry while preserving quran.ws;
- the existing quran.ws edition manifest and page bodies remain unchanged;
- a committed 604-row manual-review record establishes canonical Qaloon wording compatibility and is bound to the pinned PDF, Qaloon-source, and alias digests;
- automated checks validate review-record completeness and equality with the derived first references without claiming visual inference;
- the printed `2:49`/canonical `2:48`, printed `18:98`/canonical `18:94`, and printed `19:12`/canonical `19:11` samples remain numbering-convention regression fixtures;
- current map coverage, monotonicity, ranges, Surah starts, boundary references, Verse-to-Mushaf behavior, and page-based Wird fixtures remain valid;
- `sourcePdfPage`, dimensions, hashes, bytes, media kind, and framing metadata are emitted correctly;
- all 604 source and emitted Full page/Text focus frames pass automated bounds, containment, and edge-pixel validation, and their review artifact receives the required manual content-completeness review;
- invalid media paths, unsafe SVG, incomplete external-image descriptors, and bad rectangles are rejected;
- a failed staged import preserves the previous normalized edition;
- private input absence is reported clearly without making default CI pretend to validate it.

### Runtime Unit Tests

Focused tests prove:

- existing inline-SVG and new external-media descriptors both resolve safely;
- edition-aware path and MIME validation;
- stale loads from another edition cannot replace the active page;
- requested-page-first priority, successful load/decode readiness, and bounded neighbor behavior;
- load, decode, cancellation, and stale-edition failures clear pending readiness and preserve the current page;
- Full page, Text focus, and slider persistence callbacks;
- framing interpolation and left/right lane selection as pure data calculations;
- invalid framing falls back to Full page;
- setup distinguishes existing, empty, cleared, one-edition, and two-edition states;
- setup selection is atomic and deep-link intent is preserved;
- migration leaves the existing asset-contract marker unchanged and preserves quran.ws users' bookmarks, settings, continuity, caches, and IndexedDB data;
- a completed missing-edition selection cannot reopen setup without Clear All Data.

Unit tests assert types, data contracts, callbacks, persisted values, visible labels, and routes. They do not simulate layout, image decode, scroll geometry, or CSS cropping in jsdom.

### Real-Browser Reader Tests

Production-preview Playwright coverage and a separate recorded physical-mobile lane prove the following for the private edition. Playwright owns automated viewport, interaction, network, and offline assertions. The physical lane may use a device lab or a documented manual procedure and owns real-device clarity, decode, page-turn, and sustained-Scroll evidence.

- pages 1, representative middle pages, and page 604 render nonblank;
- Arabic glyphs, diacritics, colored marks, and borders remain visually clear at mobile DPR 2/3 and desktop;
- the winning media candidate passes clarity, load/decode, ten-page-turn, and sustained-Scroll checks on the recorded physical target device class;
- Full page has zero external whitespace and shows the complete side lane;
- Text focus removes the complete side lane and preserves every edge of the Qur'an text frame;
- intermediate framing enlarges text without horizontal scroll;
- lane-left and lane-right pages anchor correctly;
- pages with populated and empty lanes behave identically;
- all selected-frame content is vertically reachable in portrait and compact landscape;
- Single/Scroll, gestures, keyboard actions, page counters, bookmarks, route updates, and rotation continue to work;
- framing changes keep the current/dominant page anchored;
- only the intended current/neighbor media requests are eager;
- a failed or aborted destination load/decode never produces a blank committed page and remains retryable;
- an exact cached asset/rendition revisits offline, while an unfetched rendition and an unseen page fail clearly;
- an online launch replaces a stale cached Mushaf availability index with the current build's NetworkFirst response;
- existing quran.ws responsive and golden journeys remain unchanged.

Browser assertions use visible outcomes, screenshots, real scroll reachability, current routes, and request observations. Pixel/canvas checks may prove that a page is nonblank. They do not promote implementation selectors into product contracts.

The existing quran.ws reader suite remains the canonical proof for shared navigation, gesture, bookmark, route, keyboard, and layout behavior. Private-edition browser additions cover setup, external-media readiness, framing, offline rendition behavior, and one representative shared navigation/scroll journey; they do not duplicate the complete gesture matrix.

## Acceptance Criteria

- The private build contains both Qaloon editions and exactly one is active.
- Existing users remain on quran.ws without a prompt or data reset.
- Fresh and cleared private builds choose an edition once during setup.
- Switching editions requires Clear All Data.
- The private PDF never enters the browser build.
- The 604-page compatibility gate passes, and the verified shared canonical Qaloon map controls reader bridging and page-based Wird behavior.
- A true map mismatch blocks this implementation rather than introducing a second map without a separate design.
- Page assets use the single media format that passes every production-mobile spike budget.
- Full page shows the complete side lane with zero external whitespace.
- Text focus hides the complete side lane and cuts no Qur'an content.
- The bounded slider produces only reviewed frames between those endpoints.
- Mobile page turns and scrolling remain responsive with bounded eager media.
- Online edition availability cannot be supplied by a stale CacheFirst index.
- quran.ws reading behavior and assets do not regress.
