# Private Qaloun PDF Mushaf Edition Design

## Purpose

This specification adds a second Qaloon Mushaf edition to a private QuranAtlas build while preserving the current quran.ws Mushaf. It defines a deterministic PDF import, an edition-specific page map, a media-capable page contract, one-time edition selection, and configurable page framing that can show the complete side lane or remove it to enlarge the Qur'an text.

The reader remains page-based. The source PDF is never loaded or parsed in the browser.

## Source Facts

The private source is:

- original filename: `Noor-Book.com  مصحف رواية قالون عن نافع طبعة جديدة.pdf`;
- SHA-256: `4454431b2662bc10060cc9335ba13baabe1f18a6762c492d41ccf11a4083012f`;
- document pages: 630;
- source page size: `512.545 x 652.654 pt` CropBox;
- logical Mushaf pages: PDF pages 5 through 608 map to printed pages 1 through 604;
- PDF pages 1 through 4 and 609 through 630 are not reader pages;
- the PDF is vector/font based and contains no embedded full-page raster images;
- the PDF permits printing but restricts copying.

The stable private edition identity is `qalun-furatiyyah-2023-v1`, with display label `Qalun Furatiyyah 2023`. The runtime riwayah key remains `qaloon` for compatibility with the current QuranAtlas data model.

The source PDF stays outside Git and outside `public/` and `dist/`. A private import command receives its local path, verifies the exact checksum before doing any work, and writes only derived page artifacts and metadata to ignored build directories.

## Goals

- Keep the current `qalun-quran-ws-v1` edition fully supported and unchanged.
- Build the private edition from one pinned PDF without adding a runtime PDF engine.
- Use an edition-specific, verified verse-to-page map.
- Preserve existing Mushaf routes, navigation, gestures, bookmarks, Daily Wird integration, Single/Scroll layouts, and responsive behavior.
- Keep mobile memory and main-thread work bounded.
- Preserve sharp Arabic text, diacritics, colored pronunciation marks, borders, and side-lane content.
- Remove PDF media-box whitespace before page assets are emitted.
- Let the reader show the complete side lane or hide it completely while keeping all Qur'an text reachable.
- Let new or cleared private-build installations choose one Mushaf edition during setup.
- Keep existing installations on the current quran.ws edition without prompting or resetting them.

## Non-Goals

- Runtime PDF.js, browser PDF rendering, range-requested PDF pages, or shipping the source PDF.
- Arbitrary user PDF import or a generic Mushaf-import UI.
- Riwayah, translation, tafsir, or general reader-profile selection.
- Routine edition switching in Settings.
- Edition-aware bookmark schemas or preservation of page bookmarks across an edition switch.
- A targeted partial-edition reset. Edition changes use the existing Clear All Data flow.
- Pinch zoom, free panning, a generic crop editor, or user-authored per-page crop rectangles.
- OCR, selectable Mushaf text, ayah hit regions, commentary extraction, or pronunciation-rule parsing.
- Dark recoloring, CSS inversion, or generated dark variants of the private pages.
- Full-Mushaf offline installation, quota management, or download progress UI.
- Reformatting the existing quran.ws SVG page bodies.

## Decision Summary

- Import only PDF pages 5 through 608 and apply the PDF CropBox before any additional framing.
- Do not reuse the current quran.ws page map. The private edition has different page boundaries.
- Store normalized inputs and generated outputs by riwayah and edition, not by riwayah alone.
- Make the builder emit an explicit edition set and never prune a valid sibling edition merely because it is not the default.
- Keep the standard build on the current edition. A private build explicitly includes `qalun-furatiyyah-2023-v1` when its verified local source is available.
- Run a representative media spike before freezing the private page format.
- Prefer sanitized external SVG rendered through `<img>` when it passes the mobile gate. Use measured WebP variants only if SVG fails the gate.
- Keep the current inline-SVG runtime path for `qalun-quran-ws-v1`.
- Add a format-neutral manifest descriptor and normalized page-frame rectangles.
- Keep one active `mushafEditionId`. Fresh or cleared private builds choose once; existing installs retain quran.ws.
- Use Full page, Text focus, and a bounded framing slider. Any non-zero focus value uses width-based rendering and native vertical scrolling.
- Use immutable versioned URLs. Regenerated bytes require a new edition version or content identity.

## Correctness Gate: Edition-Specific Page Mapping

The current quran.ws map is not compatible with this edition. One verified example is printed page 8: the private PDF begins that page at `2:49`, while the current quran.ws Qaloon manifest begins page 8 at `2:48`.

Implementation MUST provide a normalized page-map source owned by `qalun-furatiyyah-2023-v1`. It MUST define:

```ts
type QuranRef = {
  surah: number
  verse: number
}

type MushafEditionPageMap = {
  version: 1
  riwayah: 'qaloon'
  mushafEditionId: 'qalun-furatiyyah-2023-v1'
  pageCount: 604
  pages: Array<{
    page: number
    sourcePdfPage: number
    firstVerse: QuranRef
    lastVerse: QuranRef
  }>
  verseToPage: Record<string, number>
}
```

The map is a reviewed source input, not a value inferred from the current quran.ws manifest. `verseToPage` maps each Qaloon reader verse reference to the first private-edition page on which that verse appears. A verse may be the last verse on one page and continue onto the next; page boundary metadata may therefore repeat a verse across adjacent pages.

The map gate MUST prove:

- exactly 604 ordered page rows;
- `sourcePdfPage === page + 4` for every row;
- valid Surah and Qaloon verse references;
- monotonic first/last references, allowing a continuing verse at a page boundary;
- every Qaloon reader verse reference resolves to one starting page;
- every `verseToPage` value is within 1 through 604;
- all 114 Surah starts resolve to a plausible page;
- the first page begins at `1:1` and the final page includes Surah 114;
- manual visual review of all page boundaries against the rendered source.

The import cannot proceed to runtime integration while any page boundary is unknown or disputed.

## Private Input And Build Profiles

The catalog describes the private edition without committing the PDF or an absolute machine path. It records:

- edition id and display label;
- `sourceKind: "local-pdf"`;
- expected stable source filename;
- exact SHA-256;
- document page count 630;
- reader source range 5 through 608;
- logical page count 604;
- output media policy and transform version;
- private-use provenance notes.

The import accepts an explicit local PDF path. It fails before writing output when the file is missing, has the wrong digest, has the wrong page count, or cannot render the required page range.

Normalized and generated paths include both identities:

```text
data/normalized/mushaf-pages/qaloon/qalun-quran-ws-v1/**
data/normalized/mushaf-pages/qaloon/qalun-furatiyyah-2023-v1/**
public/dataset/mushaf-pages/qaloon/qalun-quran-ws-v1/**
public/dataset/mushaf-pages/qaloon/qalun-furatiyyah-2023-v1/**
```

The default repository/CI profile continues to build quran.ws only. The private profile explicitly selects both editions and requires the local private input or already validated normalized private artifacts. Default CI MUST NOT claim it rebuilt or validated the private page bodies when the private input is unavailable.

The builder receives an explicit edition set. Output pruning is scoped to that selected set and cannot delete another selected edition. The quran.ws page bodies and edition manifest remain byte-for-byte unchanged when the private edition is added; the shared asset index intentionally gains the private entry.

## PDF Framing And Whitespace Contract

Poppler conversion MUST use the PDF CropBox. The larger MediaBox contains false outer whitespace and is not a reader frame.

Each logical page carries two reviewed, normalized rectangles:

```ts
type NormalizedRect = {
  x: number
  y: number
  width: number
  height: number
}

type MushafPageFraming = {
  fullFrame: NormalizedRect
  textFrame: NormalizedRect
  sideLane: 'left' | 'right' | 'none'
}
```

Rectangle coordinates are fractions of the emitted page asset, from 0 through 1. `fullFrame` contains the complete printed page border and the complete side lane while removing all external top, bottom, left, and right whitespace. `textFrame` contains the full Qur'an text frame and removes the complete side lane. `textFrame` MUST be contained within `fullFrame` and MUST NOT clip Qur'an glyphs, diacritics, verse markers, headers, footers, or the text-frame border.

The side lane may contain commentary or pronunciation guidance, or it may be visually empty. QuranAtlas does not interpret that content. Full page always shows the lane completely; Text focus always removes it completely. Pages whose lane is on the opposite side use their own `sideLane` and rectangles. Special-layout pages receive explicit page-specific rectangles rather than unsafe parity assumptions.

Build validation checks rectangle bounds and containment. A generated contact sheet or equivalent visual review artifact is used to verify all 604 Full page and Text focus frames. The review artifact remains scratch output and is not a product feature.

## Media Format Gate

The final private page format is selected by a production-browser spike, not assumed from file extension or compressed size.

The spike uses 12 to 20 representative pages, including:

- pages 1, 2, and 604;
- dense text pages;
- Surah starts;
- pages with red and blue pronunciation marks;
- pages with populated side lanes;
- pages with empty side lanes;
- both left- and right-lane templates;
- special first/last-page layouts.

Candidate A is a build-sanitized external SVG displayed through `<img>`. SVG scripts, event handlers, foreign objects, external URLs, remote fonts, and unsafe CSS references are rejected. Same-document references are allowed only when they pass the build allowlist. If faithful output requires constructs that cannot pass the safety contract, SVG fails the gate.

Candidate B is one or more measured WebP renditions generated from the CropBox source. Widths and quality are chosen from actual rendered-width and device-pixel-ratio evidence. The design does not mandate dual lossless renditions before measurement.

The gate measures:

- glyph, diacritic, verse-marker, and colored-mark clarity at DPR 2 and DPR 3;
- Full page and Text focus fidelity;
- raw and transferred bytes;
- cached bytes;
- first-page decode/paint latency;
- page-turn smoothness;
- sustained Scroll-mode behavior;
- decoded memory pressure;
- desktop browser zoom quality;
- rendering in production preview, not only a standalone file.

External SVG is selected when it passes safety, fidelity, latency, smoothness, and memory gates. WebP is the fallback when SVG fails. The runtime contract supports either without changing reader navigation.

## Manifest And Runtime Asset Contract

The private edition uses a media-capable manifest. Existing quran.ws manifests remain supported.

```ts
type MushafPageMedia =
  | {
      kind: 'external-svg'
      assetPath: string
      bytes: number
      sha256: string
      width: number
      height: number
    }
  | {
      kind: 'responsive-image'
      fallbackPath: string
      sources: Array<{
        assetPath: string
        bytes: number
        height: number
        mimeType: 'image/webp'
        sha256: string
        width: number
      }>
    }

type MushafManifestPageV2 = {
  page: number
  sourcePdfPage: number
  media: MushafPageMedia
  framing: MushafPageFraming
  firstVerse: QuranRef
  lastVerse: QuranRef
}
```

All asset paths remain edition-aware, same-origin, immutable `/dataset/**` paths. Index and manifest validation checks the riwayah, edition, page number, extension, MIME type, dimensions, byte count, and manifest membership. Runtime never accepts a media URL that is not declared by the active edition manifest and asset index.

The runtime page state becomes a discriminated union. The quran.ws branch continues to carry sanitized inline SVG markup. The private branch carries validated external media descriptors plus framing metadata. `MushafPageViewer` renders both through the same page-cell, accessibility, gesture, bookmark, route, and scroll contracts.

## Page Loading And Mobile Performance

The existing five-entry logical page window remains. Media readiness and decoded-media residency are treated separately.

- The requested page has highest priority.
- Single mode eagerly prepares the requested page and immediate previous/next preview only.
- Pages two positions away remain descriptor-only until Scroll mode or navigation makes them relevant.
- If WebP wins the media gate, only the current/dominant page may request the highest proven rendition eagerly. Immediate neighbors use the lower proven preview rendition; farther pages stay lazy.
- Scroll mode promotes the dominant and near-visible pages while keeping the retained logical window bounded.
- A page cannot become a swipe destination until its preview is ready.
- Failed or cancelled neighbor loads never discard the current page.

The framing control reuses the same media asset. Showing or hiding the side lane does not fetch a second page asset.

## Page Framing Interaction

The active private edition exposes three coordinated controls in Mushaf Page layout settings:

- `Full page`: framing value 0;
- `Text focus`: framing value 1;
- `Qur'an text size`: a bounded slider between the two verified frames.

The stored value is:

```ts
type MushafPageFramingValue = number // normalized and clamped from 0 through 1
```

The displayed percentage is derived from the current interpolated frame width; it is not a free scaling multiplier. The runtime linearly interpolates the reviewed `fullFrame` and `textFrame`. The page-specific interpolation automatically removes a left or right lane without horizontal panning.

At framing value 0, the reader retains the user's existing Fit page/Fit width preference. Any value greater than 0 uses effective Fit width so the Qur'an text genuinely enlarges and the complete interpolated frame remains horizontally visible. The Mushaf stage owns native vertical scrolling until the bottom of the frame is reachable. Returning to Full page restores the stored Fit page/Fit width behavior.

Framing applies consistently in Single and Scroll navigation. Changing framing:

- does not change the route or bookmark target;
- keeps the current/dominant page anchored;
- clamps the native stage scroll offset after layout;
- never adds horizontal stage scrolling;
- never clips the top or bottom of the selected frame;
- remains usable in compact landscape and safe-area layouts.

The framing controls appear only when the active edition declares valid framing metadata. quran.ws retains its existing settings and behavior.

If a page has missing or invalid framing metadata at runtime, the viewer fails open to the complete emitted page asset and disables Text focus for that page. It never guesses a crop.

## Setup, Migration, And Switching

QuranAtlas continues to store exactly one active `mushafEditionId`.

- An installation with the existing valid asset-contract marker and no new setup marker is migrated to setup-complete with `qalun-quran-ws-v1`.
- Existing users are never prompted, reset, or moved to the private edition during upgrade.
- A genuinely empty or cleared private-build installation loads the built Mushaf asset index.
- When two compatible Qaloon editions are built, setup asks the user to choose one edition.
- When only one compatible edition is built, setup selects it and continues without presenting a false choice.
- Setup writes the selected edition and completion marker atomically.
- A fresh deep link is retained through setup and resumed after a valid selection.
- A selected edition must exist in the built asset index before setup can complete.

There is no edition selector in ordinary Settings. To change editions, the user uses About > Clear All Data, which clears settings, page and verse bookmarks, continuity, and caches under the existing product contract. The next launch returns to setup. No page bookmark is carried from one edition to another, so bookmark storage remains unchanged.

## Cache And Offline Behavior

Private page assets follow the current on-demand dataset policy:

- page assets are excluded from shell precache;
- visited page assets may be stored by the existing CacheFirst dataset route;
- an offline revisit of a cached page works;
- an unseen page while offline uses the existing unavailable/error treatment;
- the product does not claim that the complete private Mushaf is installed offline.

Every private edition URL includes immutable edition identity. Changed source bytes, transforms, framing, map data, or output encoding require a new edition version or content identity. A build MUST NOT overwrite bytes at an already released immutable URL.

## Error Handling

- Missing or wrong private PDF: fail import before output mutation.
- Wrong checksum, page count, or source range: fail import.
- Missing, incomplete, or non-monotonic page map: fail build.
- Invalid framing rectangle or a frame outside the asset: fail build.
- Unsafe SVG or external reference: fail the SVG candidate; do not weaken the sanitizer.
- Missing selected edition in the runtime index: return to setup before mounting the Mushaf reader.
- Requested-page failure: use the existing visible reader error state.
- Neighbor failure: keep the current page and allow a later retry.
- Invalid runtime framing: show the full asset and disable page focus rather than crop.
- Failed preference persistence: retain the existing safe preference fallback and never block page reading.

## Verification Strategy

### Data And Build Tests

Durable script tests prove:

- exact checksum enforcement;
- CropBox conversion rather than MediaBox conversion;
- PDF pages 5 through 608 become logical pages 1 through 604;
- front/back matter is excluded;
- explicit multi-edition selection preserves both selected editions;
- build pruning cannot delete a selected sibling edition;
- the existing quran.ws edition manifest and page bodies remain unchanged;
- page-map coverage, monotonicity, ranges, Surah starts, and boundary references;
- `sourcePdfPage`, dimensions, hashes, bytes, media kind, and framing metadata are emitted correctly;
- invalid media paths, unsafe SVG, missing variants, and bad rectangles are rejected;
- private input absence is reported clearly without making default CI pretend to validate it.

### Runtime Unit Tests

Focused tests prove:

- existing inline-SVG and new external-media descriptors both resolve safely;
- edition-aware path and MIME validation;
- stale loads from another edition cannot replace the active page;
- requested-page-first priority and bounded neighbor behavior;
- Full page, Text focus, and slider persistence callbacks;
- framing interpolation and left/right lane selection as pure data calculations;
- invalid framing falls back to Full page;
- setup distinguishes existing, empty, cleared, one-edition, and two-edition states;
- setup selection is atomic and deep-link intent is preserved;
- quran.ws users are not prompted or reset.

Unit tests assert types, data contracts, callbacks, persisted values, visible labels, and routes. They do not simulate layout, image decode, scroll geometry, or CSS cropping in jsdom.

### Real-Browser Reader Tests

Production-preview Playwright coverage proves for the private edition:

- pages 1, representative middle pages, and page 604 render nonblank;
- Arabic glyphs, diacritics, colored marks, and borders remain visually clear at mobile DPR 2/3 and desktop;
- Full page has zero external whitespace and shows the complete side lane;
- Text focus removes the complete side lane and preserves every edge of the Qur'an text frame;
- intermediate framing enlarges text without horizontal scroll;
- lane-left and lane-right pages anchor correctly;
- pages with populated and empty lanes behave identically;
- all selected-frame content is vertically reachable in portrait and compact landscape;
- Single/Scroll, gestures, keyboard actions, page counters, bookmarks, route updates, and rotation continue to work;
- framing changes keep the current/dominant page anchored;
- only the intended current/neighbor media requests are eager;
- cached-page offline revisit works and an unseen offline page fails clearly;
- existing quran.ws responsive and golden journeys remain unchanged.

Browser assertions use visible outcomes, screenshots, real scroll reachability, current routes, and request observations. Pixel/canvas checks may prove that a page is nonblank. They do not promote implementation selectors into product contracts.

## Acceptance Criteria

- The private build contains both Qaloon editions and exactly one is active.
- Existing users remain on quran.ws without a prompt or data reset.
- Fresh and cleared private builds choose an edition once during setup.
- Switching editions requires Clear All Data.
- The private PDF never enters the browser build.
- The private map, not the quran.ws map, controls reader bridging and page-based Wird behavior.
- Page assets use the media format that passes the production-mobile spike.
- Full page shows the complete side lane with zero external whitespace.
- Text focus hides the complete side lane and cuts no Qur'an content.
- The bounded slider produces only reviewed frames between those endpoints.
- Mobile page turns and scrolling remain responsive with bounded eager media.
- quran.ws reading behavior and assets do not regress.
