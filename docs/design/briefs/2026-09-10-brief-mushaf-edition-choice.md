## 1. Composition and placement

**ME-P1 — Component and shell (single prescription).** New product component `src/components/settings/MushafEditionSection.tsx` rendering `SettingsGroup` (registry `settings-group`, `described` usage) with title exactly **`Mushaf edition`** and description exactly **`The Mushaf pages your reader displays. Offline downloads follow this choice.`** Rendered in `SettingsRoute` ONCE, outside the `mode` conditional, directly BETWEEN the Appearance `<SettingsGroup>` and `<OfflineDataSection />`. Group order becomes, in BOTH modes:

> mode panel ("Verse reading" / "Page layout") → Reading continuity → Appearance → **Mushaf edition** → Offline reading data → Included reading assets

Rationale: the group is causal input to the offline group (pack identity derives from the active edition, offline brief SD-4); placing it immediately above makes the dependency read top-down, and both-modes placement matches `OfflineDataSection` (verse-mode users toggle into the mushaf reader and must be able to find this choice). The group is independent of `useSettingsForm`/`settingsWriteError` — it performs its own native-store write (see ME-P6) and owns its scoped recovery; it must not depend on `OfflineDataSection` internals.

**ME-P2 — Control anatomy (single prescription).** The group content is a single `SegmentedControl` (registry `segmented-control`, `role="radiogroup"`) placed DIRECTLY in the group content flow — no `.qar-react-settings-row` wrapper, exactly like the onboarding composition (`OnboardingPageRecipe` column: instruction → SegmentedControl). One convention, not two: this is the same control, same label, same option source as first-run onboarding.

```tsx
<SettingsGroup description="The Mushaf pages your reader displays. Offline downloads follow this choice." title="Mushaf edition">
  <SegmentedControl
    label="Mushaf edition"
    onValueChange={selectEdition}
    options={options.map((edition) => ({ label: edition.label, shortLabel: edition.shortLabel, value: edition.id }))}
    value={editionValue}
  />
  {/* scoped recovery (ME-P8) renders here when present */}
</SettingsGroup>
```

- `options` come from `loadMushafEditionOptions()` verbatim — `{ id, label, shortLabel? }`. The pill face renders `shortLabel ?? label` (primitive behavior, `form-controls.tsx:140`); the accessible name is primitive-composed `${label}: ${shortLabel} — ${label}` (or `${label}: ${label}` without a shortLabel). Never render the raw edition id in the UI.
- The control is **controlled**: `value` is the persisted edition while idle, the newly selected id immediately after selection (optimistic), reverted to the last successfully persisted edition on a failed save (ME-P8).
- Known live labels (pinned for e2e): `Qalun Quran.ws` (edition id `qalun-quran-ws-v1`, verified live in the settings offline row and in `data/catalog/mushaf-asset-index.json`) and `Qalun Furatiyyah 2023` (edition id `qalun-furatiyyah-2023-v1` per dispatch). `shortLabel` values are whatever the built `/dataset/indexes/mushaf-assets.json` ships; e2e must compose expected names from live index data, not baked literals (see Open items).
- **Persisted-id read and its failure mode:** the id is read from the native setting (`readNativeSettings(['mushafEditionId'])` — the `SettingsRoute` framing effect's existing read, `SettingsRoute.tsx:59-75`). If the read REJECTS, the section must not hang in loading and must not leak an unhandled rejection: when no persisted id is confirmable, fall back to `DEFAULT_READER_ASSET_PROFILE.mushafEditionId` for the control value (the shipped baseline; options loading proceeds independently). A failed read during a later refresh retains the last good value — never blanks it (advisor delta 6).

**ME-P3 — Not designed here (boundary).** No onboarding changes (its flow already writes the same setting). No `OfflineDataSection` visual changes. No new CSS classes, no new registry entry (matching shipped practice: `OfflineDataSection` has none; the group inherits `settings-group`'s ownership and forbidden-use rules). No page-level status for this group — the global `settingsWriteError` banner stays scoped to the `useSettingsForm` queue and never reports edition saves.

## 2. States (single prescription each)

**ME-P4 — Loading (options resolving).** Until `loadMushafEditionOptions()` resolves: the group content renders the group heading/description plus a single placeholder line carrying the label copy, `aria-busy="true"` on the group content wrapper — the SD-P5 neutral-placeholder idiom (name present, no control, no status). No spinner, no skeleton, no "Loading" string. The typical resolution is a single cached fetch; degraded worlds hold this state until the `online` event or overlay reopen (ME-P7). Instant swap to ready — no transition. Options-fetch rejection → ME-P7, not an error surface; persisted-id read rejection → ME-P2 fallback, never an indefinite loading state (advisor delta 6).

**ME-P5 — Ready (metadata available).** The SegmentedControl renders with one pill per available edition, the persisted edition selected. Selected-pill treatment outside a row wrapper is the primitive's own selected class (`--qa-react-nav-control-selected-bg` + accent text, `index.css:2219-2222`); the settings-row variant (`--qa-react-settings-selected` + `--qa-react-settings-selected-text`, `index.css:1220-1223`) is the row-wrapped alternative — see Open items for the visual reviewer's standing call. State is never color-only: `aria-checked` + the selected class carry it.

**ME-P6 — Switching (the write).** On select: value updates optimistically (ME-P5), then the section writes through `writeMushafEditionSelection(editionId)` — the exact onboarding write path (`native-reader-store.ts:67-74`, persists `mushafEditionId` AND `mushafEditionSetupVersion`). The write is a local IndexedDB transaction: no network gate, no `navigator.onLine` check, no persistence prompt. No spinner during the write (a local write is fast; a per-selection spinner would flicker — onboarding's `Spinner label="Saving Mushaf setup"` exists because navigation follows, which is not the case here). The control is never disabled while a write is in flight (framing precedent).

- **Write ordering guard (advisor delta 2 — required).** `writeNativeMushafEditionSelection` opens a fresh connection/transaction per call, so two rapid selections can commit out of order. The section MUST serialize its writes through an in-component queue (the `useSettingsForm.writeQueueRef` idiom: chain each write onto the previous one's settled promise, `useSettingsForm.ts:74-79`), or equivalent epoch guard. Only the LATEST operation may update the optimistic value, revert state, failure status, retry target, and fire the §3 wake-up emit; superseded operations resolve silently.
- **Commit-vs-notification separation (advisor delta 8).** The write operation's success/failure classification is ONLY the `writeMushafEditionSelection(editionId)` result. The post-commit preferences read used to build the §3 emit detail (`readNativeReactReaderPreferences()` — an independent IndexedDB open) is NOT part of the write op: its rejection must never trigger ME-P8 (no false revert, no false save-failure status for a commit that landed). After a commit, the wake-up emit is ALWAYS issued — on detail-read failure, emit with whatever detail is available (an empty detail object is acceptable: subscribers already treat missing detail as "re-read native state", `reader-preferences.ts:29-31`). **Emitter signature widening (advisor delta 10, required):** `emitReactReaderPreferencesChanged` is currently typed `(preferences: ReactReaderPreferences)` (`reader-preferences.ts:21`) while the event it dispatches is already `CustomEvent<Partial<ReactReaderPreferences>>` (`reader-preferences.ts:10`) — widen the parameter to `Partial<ReactReaderPreferences>` (type-only, aligns the signature with the event contract it already wraps) so the empty-detail dispatch type-checks. NEVER fall back to emitting `DEFAULT_REACT_READER_PREFERENCES` as detail: its set `theme`/`nightMode` would make App's listener reset the user's appearance (`App.tsx:92-95`); an empty detail no-ops there by guard. The emit is a global window dispatch issued unconditionally post-commit; it is NOT gated on this section's mount lifetime — only local React state updates are unmount-guarded, never the emit.
- On write rejection: ME-P8. On commit with failed detail read: side effects still fire (§3).

**ME-P7 — Offline-metadata-unavailable (degraded).** `loadMushafEditionOptions()` throws (fetch failure, SPA-fallback HTML 200 → `response.json()` rejects, invalid index — all verified against source) or resolves empty: the control cannot render. The group content renders the label line plus one muted status line (`<p class="qar:m-0 qar:text-sm qar:text-muted">`), exact text **`Edition options unavailable right now`** — no `Status` block, no icon, no button (degraded ≠ failure; the offline group's `SD-P6` no-button precedent). The active edition is silently unchanged. Re-resolution contract, identical to offline SD-P4: (a) `window` `online` listener added on mount, removed on cleanup; (b) overlay reopen (SettingsRoute remounts per open). The empty-index case (parse succeeds, zero available assets) collapses into the same line — one degraded treatment, no branching. A FAILED re-resolution (retry throws again) preserves whatever the section already shows: an existing ready control keeps its options and value; a degraded state stays degraded. Refreshes never replace good data with worse data (advisor delta 7).

**ME-P8 — Save failure.** The write rejects and the failed write is still the latest operation: revert `value` to the last successfully persisted edition, and render inside the group content, directly under the control: a polite inline status `<p role="status" aria-live="polite" class="qar:m-0 qar:text-sm qar:leading-6 qar:text-danger">` with exact text **`Could not save Mushaf edition`**, plus `Button size="sm" variant="secondary"` with exact text **`Retry saving Mushaf edition`**. This is the MushafSettings framing-write pattern verbatim (`MushafSettings.tsx:83-90`: polite `role="status"`, not the assertive global banner — a recoverable non-blocking save failure belongs polite). The `Retry` text is lengthened because the sheet already hosts other `Retry` buttons (settings-write banner, framing row, offline rows); role+name must stay unambiguous for e2e. No forced focus move on failure (framing precedent; the polite live region announces).

- **Retry targets the FAILED id, not the reverted value (advisor delta 3).** After a revert, the control shows persisted A while the user's intent was B — a naive "retry current value" would re-write A (a no-op). The section keeps a failed-target ref (the `retryMushafPageFramingRef` idiom, `useSettingsForm.ts:157-185`): Retry re-attempts the write of the FAILED edition id. A newer selection clears/supersedes the failed target (last-write-wins, ME-P6). A stale failure must never revert a newer successful choice: revert and status apply only if the failed write is still the latest operation.

**ME-P9 — Single available edition.** If the index lists exactly one edition, render the one-pill control (honest; mirrors reality) — no auto-write, no special case. The persisted edition is already that edition for every onboarded user (onboarding auto-completes single-edition setups, `OnboardingRoute.tsx:202-209`), so the pill renders selected.

**ME-P10 — Persisted edition absent from the resolved options (advisor delta 9; distinguished degraded substate).** Options resolved successfully but none matches the persisted edition id (edition unpublished / `not-built` / index changed under an old selection). The primitive CANNOT represent "none selected": `selectedValue = selectedOption?.value ?? firstEnabledValue` (`form-controls.tsx:105-106`) silently marks the FIRST pill selected — a false claim about the active edition. Therefore: render NO control. In its place, the muted status line (same treatment as ME-P7, `qar:m-0 qar:text-sm qar:text-muted`) with exact text **`Your selected Mushaf edition is no longer available`** — deliberately the boot missing-gate's exact wording (`OnboardingRoute.tsx` 'missing' branch title): one string, one meaning, already in the e2e vocabulary. No auto-write, no silent correction to another edition. Recovery belongs to the EXISTING boot missing-gate path (About → clear saved data), not to a second, forking recovery flow here. Re-resolution on `online`/reopen applies: if the persisted edition reappears in the options, the normal ready state (ME-P5) resumes. The reader keeps running the persisted edition throughout — the index gates the CHOICE UI, not the active setting.

## 3. Side effects after a successful save (the wiring contract)

The write itself is step 1; the switch is only real when the surfaces that derive from the active setting re-resolve. The single existing change channel is `emitReactReaderPreferencesChanged(preferences)` / `subscribeReactReaderPreferencesChanged` (`reader-preferences.ts:14-30`) — already fired by every settings write and already subscribed by `App.tsx`, `MushafRoute`, `ReaderRoute`, and `SettingsRoute`. The implementer MUST wire, in this order:

1. **Persist selection** — `writeMushafEditionSelection(editionId)` (ME-P6). On success, emit the change: `emitReactReaderPreferencesChanged(await readNativeReactReaderPreferences())`. The event detail carries the React reader preferences (unchanged by this write); it is the wake-up channel — every consumer below re-reads what it owns from the native store. The detail read is best-effort (ME-P6 separation): if it rejects, still emit with an empty/partial detail (emitter parameter widened to `Partial` — ME-P6) — a committed switch must never lose its wake-up because a secondary read failed, and a default-prefs detail must never be fabricated (appearance-reset risk).
2. **Offline rows re-derive** — `OfflineDataSection` subscribes to the change event and bumps its existing `reloadKey`, re-running its metadata effect (`readActiveReaderProfile` + `loadMushafEditionEntries` + `loadDatasetByteSizes`, `OfflineDataSection.tsx` second mount effect). Pack ids re-derive from the new active profile (SD-4): the newly active edition's row shows its own record state; a pack downloaded for the previously active edition STAYS downloaded and reappears downloaded when the user switches back (dispatch behavior fact — no removal, no prompt, no re-download).
3. **Framing capability reload** — `SettingsRoute`'s framing effect (`loadMushafFramingCapability`, `SettingsRoute.tsx:59-75`) re-runs for the new edition id on the same event; in mushaf mode the Qur'an text size row appears or disappears per the returned `hasValidFraming` (editions without text-frame data lose the row — the existing gate, no change).
4. **Mushaf base re-resolves** — the mounted `MushafRoute` (when the overlay opened over `#/m/…`) extends its existing `subscribeReactReaderPreferencesChanged` effect (`MushafRoute.tsx:173-201`) to re-run `loadActiveMushafSettings()` and apply fresh `activeSettings`. `useMushafProfileSession` is keyed on `profile.mushafEditionId` (`MushafRoute.tsx:110-118`), so the page window re-resolves to the new edition automatically; the requested page number is preserved. Page identity is safe by construction: every acceptable edition passes `isAvailableQaloonMushaf`'s `pageCount === 604` gate (`mushaf-edition-setup.ts:116-127`), so no page-clamping path can trigger. The base repaints behind the scrim while the overlay stays open — correct and desired: the user sees their choice land.
5. **Included assets inventory refresh (advisor delta 1 — corrected)** — `IncludedAssetsSection` re-resolves its rows on the same event. Its current mount effect resolves `DEFAULT_READER_ASSET_PROFILE` (`IncludedAssetsSection.tsx:30-44`), NOT the active profile — for a v1-active user the shown "Mushaf: Qalun Quran.ws" row is correct only by coincidence. The refresh MUST resolve the CURRENT native profile: read the native `mushafEditionId` (and other profile fields) and pass the resolved profile to `resolveReaderAssetProfileRows`, keeping the `DEFAULT_READER_ASSET_PROFILE` fallback only for fields with no persisted value. Ruled IN scope: a stale "Mushaf: Qalun Quran.ws — Included" row after a switch to Furatiyyah would visibly contradict the choice made one group above. Abort stale fetches (existing `AbortController` pattern, re-created per refresh).

**Re-derivation safety rules (advisor delta 4 — apply to every §3 consumer).** The reused event fires on EVERY settings write (theme, font size, translation…), and its detail carries no edition id. Therefore:
- **Filter by tracked active edition.** Each §3 subscriber (offline section, framing effect, mushaf route, included-assets) tracks the last active edition id it resolved and re-runs its resolution ONLY when the freshly read native `mushafEditionId` differs from the tracked one. Unchanged edition → the event is ignored (no re-fetch on font/theme writes).
- **Preserve prior data on refresh failure.** A re-resolution that fails (offline index fetch, read rejection) keeps the consumer's existing state — never swaps good labels/metadata for `null`/fallbacks. `OfflineDataSection`'s `Promise.all` catch and `loadActiveMushafSettings`'s catch (`MushafRoute.tsx:582-603`, which returns the DEFAULT edition wholesale) must not feed their fallback results into a refresh: refresh error → keep current state; only a CONFIRMED new read applies.
- **Latest-request-wins.** Every async re-resolution is guarded (epoch/`active` flag/abort) so out-of-order resolutions cannot restore an older edition: rapid A→B→A switching applies only the newest read; a stale success after a newer write is discarded.

No other surface reacts: themes, typography, bookmarks, and continuity state are edition-independent. The reader route (`#/s/…`) does not reload. No hash changes, no navigation, no overlay close is forced.

## 5. Per-viewport layout

**1280×900 (desktop rail).** Sheet `min(28rem, 100vw − 24px)` right-anchored (verified live). The group renders between Appearance and Offline reading data in the existing `--qa-react-settings-space-4` grid. Group content: heading block, description, then the segmented control at content width, pills sized by their labels (two pills fit the ~400px content column with either shortLabels or full labels; `qar:truncate` guards pathological lengths — pill min-width behavior is the primitive's, unchanged). The save-failure status + Retry stack under the control (`qar:grid qar:gap-2` idiom, MushafSettings framing-error block). All groups remain above the fold-or-scroll as shipped; this group adds ~96px (heading + description + control) — the body scrolls exactly as today.

**375×812 (mobile full-bleed).** Sheet full-bleed `100dvh`, scrollable body. The control sits at full content width (the plain grid wrapper from ME-P2 carries the width; the row-scoped `width: 100%` radiogroup rule at `index.css:1403-1406` does not apply outside a row wrapper — pills share the width per the primitive's flex layout). Description wraps to at most two lines. Both pills + labels must fit 335px content width; with the known labels they do. No horizontal overflow (`scrollWidth === 375`, verified pattern from the live walk).

**Both viewports, both modes, all states:** no layout shift between verse and mushaf modes (same group, same place); the degraded state reserves the same vertical space as the control row (label line + status line ≈ control height) so reopening online does not jolt the scroll position.

## 6. Themes + night

All color through existing `--qa-react-*` settings-family tokens via owned primitives: group card `--qa-react-settings-group` + `--qa-react-settings-group-border`, divider `--qa-react-settings-divider`, muted `--qa-react-settings-muted`, selected pill per ME-P5, danger text `--qa-react-text-danger` → `--qa-react-danger` on the save-failure line. Three-theme correctness is by construction (light/sepia/dark token derivations, `semantic.css`); dark's deeper `--qa-react-settings-shadow` covers the group like every other group. Night mode: the `.qar-react-night-shift` wash covers the sheet uniformly; no per-component dimming. The degraded and failure states introduce no new color usage.

## 7. Motion / reduced-motion

This brief ADDS no motion: no animation, transition, or keyframe. Selection is an instant class/state change; loading→ready and ready→degraded are instant swaps; the save-failure block appears instantly. The SegmentedControl has no shipped transition (verified: selected state is class-driven, `index.css:2219-2222`); the reader's re-resolve behind the scrim uses the existing page-window behavior, not a new animation. Reduced-motion (`prefers-reduced-motion: reduce`): nothing to kill — state changes are already instant and remain fully visible.

## 8. Focus and 44px targets

- **Focus order:** group content is one focusable radiogroup (native radio inputs, arrow-key navigation — primitive behavior) plus, in the failure state, one Retry button. Both sit in natural DOM order between the Appearance group and the offline rows. Sheet focus trap unchanged.
- **Focus-visible:** the primitive's ring — `outline: 2px solid var(--qa-react-focus); outline-offset: 2px` via `.qar-react-segmented-option:has(input:focus-visible)` (`index.css:2214-2217`); Retry via the shared `Button` ring. No inset overrides (no clipping container).
- **Targets:** the SAME primitive at the SAME size is already signed off in the Navigation mode row and onboarding; the visual reviewer re-confirms pills ≥44px tall in this placement. Retry is `size="sm"` with `qar:min-h-11` → 44px. No icon-only controls.

## 9. Design rulings (decided defaults — recorded so the implementer never asks)

1. **Both modes, above Offline reading data** (not mushaf-only, not after the mode panel): causal chain reads top-down; verse-mode users need reachability. Ruled: ME-P1 order.
2. **Control directly in group content, no settings-row wrapper** (not a two-column row with an empty copy cell): parity with onboarding's identical control; the group heading already names the choice. Ruled: ME-P2/ME-P5.
3. **Optimistic apply, no spinner, no disabling, last-write-wins — with a serialized write queue:** applies instantly like every settings control; the queue (ME-P6) exists because the native write path has no cross-call ordering guarantee, unlike `useSettingsForm`'s shared queue. Ruled: ME-P6.
4. **Polite inline failure with lengthened Retry (`Retry saving Mushaf edition`), no focus move, revert-on-failure, retry-targets-failed-id:** framing-block precedent plus the failed-target ref from `persistMushafPageFraming`. Ruled: ME-P8.
5. **One degraded treatment for all metadata-unavailable shapes** (throw, SPA-fallback HTML, empty index) with no Retry button; failed re-resolutions preserve shown data: matches the offline group's `SD-P6` no-button degraded row; `online`/reopen re-resolution is the recovery. Ruled: ME-P7.
6. **One-pill control when only one edition exists:** honest, zero special casing. Ruled: ME-P9.
7. **No registry entry for the new component:** matches shipped practice (`OfflineDataSection` unregistered); `settings-group` ownership/consumer rules govern usage. Ruled: ME-P3.
8. **IncludedAssetsSection refresh ruled into the wiring contract, resolving the CURRENT native profile** (not the default-profile constant it ships with): a stale or wrong-edition inventory row contradicts the choice one group above. Ruled: §3 step 5.
9. **Event reuse with mandatory edition-change filtering (no dedicated edition event):** reuse keeps one change channel; filtering plus preserve-on-failure plus latest-wins (§3 safety rules) closes the breadth and staleness holes the shared channel would otherwise open. A dedicated edition-change event remains a future shared-channel evolution, out of scope. Ruled: §3.
10. **Commit and notification are separate concerns (advisor deltas 8+10):** only the native write rejection drives ME-P8; the wake-up emit always fires post-commit, empty `Partial` detail acceptable (emitter signature widened, type-only), defaults never fabricated as detail, never cancelled by unmount. Ruled: ME-P6/§3 step 1.
11. **Absent-edition world renders a line, not a forked recovery flow (advisor delta 9):** the primitive cannot show "none selected" (`firstEnabledValue` fallback would lie), and the boot missing-gate already owns this world's recovery. Ruled: ME-P10.

## 10. Open items

1. **`shortLabel` values are deploy-time data.** The tracked anchor (`data/catalog/mushaf-asset-index.json`) carries only v1 and no `shortLabel`; the built `/dataset/indexes/mushaf-assets.json` (generated by `data:build` against the pinned release artifacts) is the source for both editions' `label`/`shortLabel`. The brief pins the composition rule (`shortLabel ?? label`, primitive-composed accessible name) and the two known labels; e2e must derive expected names from live index data. Director ruling stands: no shortLabel is invented here.
2. **Visual weight of the ready-state selected pill** (`--qa-react-nav-control-selected-bg` + accent text vs the settings-row `--qa-react-settings-selected` family tint): both are shipped, token-backed treatments; the ui-visual-reviewer judges the rendered result at both viewports in all three themes and may direct the row-wrapped variant purely for tint consistency, with no other change.
3. **OfflineDataSection fetch sharing:** this group and the offline group both fetch the edition index per overlay open. Two cached GETs are acceptable; if the implementer deduplicates via a shared module-level cache, the abort-on-unmount pattern must be preserved per consumer (SD-P5). No design constraint beyond that.
4. **e2e coverage for the §3 safety rules:** the filtering/preserve-on-failure/latest-wins rules are behavioral contracts best proven by e2e (switch → offline rows re-derive; theme write → no index refetch; failed refresh → labels retained). The brief specifies behavior, not test placement; the orchestrator owns suite topology.
